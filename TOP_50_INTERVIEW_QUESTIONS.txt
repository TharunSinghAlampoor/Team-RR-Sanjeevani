Q1: How does Spring Security 6 handle stateless JWT-based authentication in this application?
Answer:
Spring Security 6 handles stateless authentication by configuring SessionCreationPolicy.STATELESS 
in the SecurityFilterChain bean. A custom JwtAuthenticationFilter intercepts incoming HTTP requests, 
extracts the JWT token from the "Authorization: Bearer <token>" header, validates the signature using 
Keys.hmacShaKeyFor(secretBytes), extracts user email/claims, loads user details from UserRepository, 
and constructs a UsernamePasswordAuthenticationToken object. This token is populated into 
SecurityContextHolder.getContext().setAuthentication(auth), allowing Spring Security to authorize 
downstream controller requests without maintaining server-side HTTP sessions.

--------------------------------------------------------------------------------

Q2: Why did Spring Security 6 replace .authorizeRequests() with .authorizeHttpRequests(), and how are request matchers configured?
Answer:
In Spring Security 6 (Spring Boot 3), .authorizeRequests() was deprecated in favor of 
.authorizeHttpRequests(), which utilizes AuthorizationManager rather than AccessDecisionManager. 
When defining public endpoints, request matchers must account for path wildcards. For example, 
.requestMatchers("/categories/**") matches subpaths like /categories/1, but does NOT match the 
root path /categories. Therefore, both exact paths (/categories) and wildcard subpaths (/categories/**) 
must be explicitly declared inside .permitAll().

--------------------------------------------------------------------------------

Q3: How is Servlet context path stripping handled when server.servlet.context-path=/api is configured?
Answer:
When server.servlet.context-path=/api is specified in application.properties, the servlet container 
strips the /api prefix before passing the URI path to Spring Security filters. Consequently, path 
matchers in SecurityFilterChain should match endpoints relative to the root context (e.g., 
.requestMatchers("/auth/login", "/products", "/categories").permitAll()), while client requests 
hit http://localhost:8080/api/auth/login.

--------------------------------------------------------------------------------

Q4: Why is CORS configured centrally in SecurityFilterChain rather than relying solely on @CrossOrigin annotations on Controllers?
Answer:
Spring Security filter chains execute BEFORE Spring MVC dispatches requests to controllers. When a browser 
sends a cross-origin preflight HTTP OPTIONS request (e.g. from Vite http://localhost:5173 to Spring Boot 
http://localhost:8080), if security CORS is not configured, Spring Security blocks the OPTIONS request 
with HTTP 401/403 before Spring MVC can process controller @CrossOrigin annotations. Central CORS 
registration via .cors(cors -> cors.configurationSource(corsConfigurationSource())) guarantees 
preflights are handled at the security boundary.

--------------------------------------------------------------------------------

Q5: Trace the step-by-step filter execution inside JwtAuthenticationFilter (OncePerRequestFilter).
Answer:
1. Intercepts request via doFilterInternal(request, response, filterChain).
2. Extracts "Authorization" header and validates "Bearer " prefix.
3. Parses JWT claims using JwtService; if expired or invalid, throws JwtException.
4. Extracts email and verifies SecurityContextHolder.getContext().getAuthentication() is null.
5. Loads User entity from database and validates account status (ACTIVE).
6. Constructs UsernamePasswordAuthenticationToken with granted authorities (ROLE_USER/ROLE_ADMIN).
7. Sets WebAuthenticationDetailsSource and stores token in SecurityContextHolder.
8. Invokes filterChain.doFilter(request, response) to continue execution.

Q6: How does BCryptPasswordEncoder(12) secure user passwords against rainbow table and brute-force attacks?
Answer:
BCryptPasswordEncoder uses the Blowfish cipher adaptive hashing algorithm incorporating a 128-bit 
random salt and a configurable cost factor (work factor 12). The random salt ensures identical plain 
passwords produce distinct hashes, rendering precomputed rainbow tables useless. A cost factor of 12 
requires 2^12 (4,096) hashing rounds per password calculation, drastically slowing down brute-force 
cracking attempts while keeping server verification latency under 100ms per login request.

--------------------------------------------------------------------------------

Q7: Why are Data Transfer Objects (DTOs) like ProductDto and OrderDto used instead of exposing JPA Entities in API responses?
Answer:
1. Security: Prevents over-posting/mass-assignment vulnerabilities and hides sensitive entity 
   attributes (e.g., BCrypt password hashes, internal database IDs).
2. Performance: Eliminates LazyInitializationException and circular JSON serialization loops 
   when serializing bi-directional entity relationships.
3. API Decoupling: Allows internal database schema refactoring without breaking client API contracts.
4. Validation: Enables clean Jakarta Bean Validation (@NotNull, @NotBlank, @Min) on request payloads.

--------------------------------------------------------------------------------

Q8: How does the backend prevent LazyInitializationException when retrieving entity relationships outside transactional boundaries?
Answer:
LazyInitializationException occurs when Jackson JSON serializer attempts to access uninitialized 
Hibernate lazy proxy collections outside an active @Transactional database session. The application 
prevents this by mapping entity objects directly into decoupled DTO instances inside service layer 
methods while the database transaction is still active (@Transactional), returning fully initialized 
DTO objects to the controller.

--------------------------------------------------------------------------------

Q9: How are circular JSON serialization loops (Order -> OrderItem -> Order) prevented?
Answer:
Circular serialization loops occur when Jackson attempts to serialize bi-directional JPA mappings. 
This is prevented by:
1. Mapping entities to DTOs where child DTOs do not contain references back to parent objects.
2. Annotating entity relationship fields with @JsonIgnore.
3. Using @JsonManagedReference on the parent entity side and @JsonBackReference on the child entity side.

--------------------------------------------------------------------------------

Q10: How does @RestControllerAdvice in GlobalExceptionHandler handle validation errors and domain exceptions?
Answer:
GlobalExceptionHandler catches runtime exceptions thrown across all controller endpoints:
1. MethodArgumentNotValidException: Triggered by failed DTO validations (@NotBlank, @Min). It extracts 
   field-level error messages and returns HTTP 400 Bad Request with structured JSON maps.
2. ResourceNotFoundException / AuthException: Maps custom business exceptions to HTTP 404 or HTTP 401 
   with standardized ApiResponse payloads (timestamp, message, status).
3. Exception: Silently logs full stack traces server-side and returns HTTP 500 Internal Server Error 
   with a safe error message to prevent sensitive stack leaks.

Q11: How does @Transactional guarantee ACID compliance during order placement?
Answer:
In OrderService.createOrder():
1. Stock Verification & Reduction: Decrements stock_quantity in products table.
2. Order Insertion: Saves Order entity to orders table.
3. Order Items Insertion: Saves list of OrderItem entities to order_items table.
4. Cart Cleanup: Deletes user's items from cart_items table.
If any step fails (e.g. insufficient stock or payment error), @Transactional triggers an automatic 
database rollback of all pending INSERT/UPDATE/DELETE queries, maintaining complete ACID data integrity.

4. Parses the returned Razorpay order object, extracting razorpay_order_id (e.g. order_N123xyz), and

Q13: Pin-to-pin, how is Razorpay HMAC SHA-256 payment signature verification performed on the server?
Answer:
After client payment completion, the backend receives razorpay_order_id, razorpay_payment_id, and 
razorpay_signature. The backend:
1. Concatenates string payload: razorpay_order_id + "|" + razorpay_payment_id.
2. Calculates cryptographic HMAC SHA-256 hash of the payload string using merchant API Key Secret.
3. Converts hash to hexadecimal string.
4. Compares generated hex signature with received razorpay_signature using MessageDigest.isEqual().
5. If signatures match, payment is confirmed genuine; backend updates order status to PAID and inserts 
   record into payments table.

Q15: Pin-to-pin, trace the execution flow of user login (/api/auth/login).
Answer:
1. Client POSTs email and password payload to AuthController.login().
2. RateLimitConfig checks client IP address against login rate limits.
3. AuthService fetches User by email from UserRepository; throws AuthException if not found.
4. Validates password via passwordEncoder.matches(rawPassword, user.getPassword()).
5. Verifies user.getAccountStatus() == "ACTIVE".
6. Generates signed JWT token via JwtService.generateToken(email, role) expiring in 24 hours.
7. Constructs LoginResponse containing JWT token and UserProfile object; returns HTTP 200 OK.

Q16: How does the OTP password reset workflow function across OtpService and EmailService?
Answer:
1. User requests password reset (/auth/forgot-password).
2. OtpService generates a 6-digit cryptographically random numeric OTP code using SecureRandom.
3. Saves record to otps table with email, otp_code, and 10-minute expiry timestamp.
4. EmailService sends an HTML email formatted with Sanjeevani healthcare branding.
5. User submits OTP to /auth/verify-otp; backend checks code and expiry time.
6. Upon successful verification, user calls /auth/reset-password to update BCrypt hashed password 
   in users table, and OtpService purges the used OTP.

Q18: How does RateLimitConfig prevent brute-force attacks on authentication endpoints?
Answer:
RateLimitConfig implements an in-memory sliding window rate limiter tracking request timestamps per 
client IP address (request.getRemoteAddr()):
1. Login Rate Limit: Restricts IP addresses to 10 login attempts per 15-minute window.
2. OTP Rate Limit: Restricts IP addresses to 3 OTP request attempts per 10-minute window.
If request count exceeds thresholds, it throws AuthException returning HTTP 429 Too Many Requests.

Q20: When are FetchType.LAZY vs FetchType.EAGER used, and how does CascadeType.ALL operate?
Answer:
1. FetchType.LAZY: Default for @ManyToOne and @OneToMany collections. Lazy loading defers database 
   querying of related entities until explicitly accessed, preventing heavy unnecessary N+1 queries.
2. FetchType.EAGER: Forces immediate join loading of associated entities upon parent fetch. Used sparingly 
   for small mandatory single-item mappings.
3. CascadeType.ALL: Propagates all entity state transitions (PERSIST, MERGE, REMOVE, REFRESH) from parent 
   to child entities (e.g. deleting an Order automatically cascades deletion to child OrderItem rows).

3. Foreign Key Indexes: Created on products.category_id, order_items.order_id, and cart_items.user_id

Q29: How do Axios request interceptors automatically inject JWT authentication headers?
Answer:
In shopService.js and authService.js:
axiosInstance.interceptors.request.use(
  (config) => {
    const token = localStorage.getItem('token');
    if (token) {
      config.headers['Authorization'] = `Bearer ${token}`;
    }
    return config;
  },
  (error) => Promise.reject(error)
);
This guarantees every API request automatically attaches JWT tokens without manually passing headers.

Q30: Pin-to-pin, how does shopService.js handle 401 unauthenticated responses to allow smooth guest browsing?
Answer:
When unauthenticated guest users browse public catalog routes (/categories, /products), secondary API 
calls (e.g. fetching user cart or wishlist) return HTTP 401 Unauthorized. 
The response interceptor catches 401 errors:
1. Checks if localStorage contains an active token.
2. If NO active token exists (guest browsing), catches the error silently and resolves with empty 
   default arrays ([]).
3. If an active token WAS present (expired session), clears invalid storage credentials and triggers logout.
This prevents guest browsing from crashing UIs or causing infinite redirect loops.

Q33: How does OrdersModal.jsx implement immutable reverse chronological sorting (Latest to Oldest)?
Answer:
To sort order history without mutating state arrays:
const sortedOrders = [...orders].sort((a, b) => {
  const timeA = a.createdAt ? new Date(a.createdAt).getTime() : 0;
  const timeB = b.createdAt ? new Date(b.createdAt).getTime() : 0;
  if (timeA !== timeB) return timeB - timeA;
  const idA = Number(String(a.orderId || '').replace(/[^0-9]/g, '')) || 0;
  const idB = Number(String(b.orderId || '').replace(/[^0-9]/g, '')) || 0;
  return idB - idA;
});
This ensures orders display from newest to oldest cleanly.
